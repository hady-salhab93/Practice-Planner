# Define the minimum useful practice-and-review loop

## Question

For one real Sprint practicing "Take the Time," what must the application support from preparation through review to be useful, and which capabilities can initially remain basic or wait? Establish the first-version boundary from the user's workflow without choosing detailed screens, schemas, timer rules, or implementation tasks.

## Resolution

The user confirmed the following minimum useful loop on 2026-10-11:

1. Collect material and break it into manageable pieces. Breakdown is necessary, not an optional organizing enhancement.
2. Select material for a Sprint.
3. Pick a piece and time intentional practice. Picking the item is sufficient; integrated sheet music, recordings, or other resources are not required for this version.
4. Optionally write daily observations to support reflection at the end of the Sprint.
5. Review time distribution, untouched material, and observations. Observations support the user's interpretation, not an application-generated assessment of musical improvement.
6. Reuse and refine material for the next Sprint.

This confirms the first-version workflow, not detailed feature specifications or implementation authorization. Feature boundaries, interaction rules, persistence behavior, and acceptance scenarios still need separate agreement.
